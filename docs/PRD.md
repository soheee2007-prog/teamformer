# PRD: 팀 프로젝트를 위한 팀 편성 웹 앱

- 근거 문서: 중간 과제 공고(이하 "공고"), 연습용 명단 `쉬움.csv`, `중간.csv`, `어려움.csv`
- 마감: 2026-11-02(월) 23:59. 채점: 11/3~11/4, 공개하지 않은 채점 시나리오 3개(쉬움, 중간, 어려움)로 자동 채점
- 이 문서는 공고의 요구를 그대로 옮기고, 공고가 정하지 않은 부분은 "설계 결정"으로 표시한다

## 1. 목표와 성공 기준

가상 학생들이 스스로 팀을 짜고, 모집 마감 뒤 남은 학생은 AI가 배정하며, 앱이 AI의 답을 규칙으로 검사하는 Streamlit 앱을 만든다.

성공 기준:
1. 연습 시나리오 3개(공고 부록)의 모든 단계에서 `result`의 첫 단어가 기대 결과와 같다.
2. 마감, 배정, 확정 뒤 모든 팀이 2.3절의 규칙을 지킨다. AI가 3차까지 실패해도 지킨다.
3. 채점 시나리오가 연습 시나리오와 학생 수(8~16명), 팀 수(3~4개), 이름, 역할, 순서가 달라도 같은 규칙으로 동작한다. 시나리오에 맞춘 하드코딩은 하지 않는다(공고 6.3절 19번).
4. 보안과 제출 감점 항목(공고 6.3절)에 하나도 걸리지 않는다.

## 2. 사용자

| 사용자 | 로그인 | 하는 일 |
|---|---|---|
| 학생 | 학번 + 비밀번호(모두 `1234`) | 팀 목록과 팀원(주 역할, 보조 역할)을 봄, 팀에 지원, 내 팀에 들어온 지원에 찬성 또는 거부 |
| 관리자 | 학번 `admin` + `ADMIN_PASSWORD` | 명단 CSV와 팀 수로 처음 상태 만들기, 모집 마감, AI 배정, 배정안 확정 |

- 관리자 계정은 앱이 시작할 때 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신한다. 명단을 다시 올려도 남긴다.
- 학생 계정으로는 관리자 기능을 볼 수도, 실행할 수도 없다. 화면에서 숨기는 것에 더해 처리 함수에서도 관리자인지 확인한다.
- 구글 로그인(`st.login`)은 쓰지 않는다.

## 3. 역할과 팀 규칙 (공고 2.2~2.3절)

- 역할 6개: 기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자
- 학생마다 주 역할 1개, 보조 역할 0~2개. 학생이 바꾸지 않는다.

| 규칙 | 내용 |
|---|---|
| 정원 | 확정한 팀은 모두 2~4명(빈 팀 없음) |
| 주 역할 중복 | 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 됨 |
| 필수 포함 역할 | 모든 팀에 기획자를 맡을 학생과 웹 프로그래머를 맡을 학생이 **서로 다른 사람으로** 1명씩. 주 역할이나 보조 역할로 맡을 수 있음 |

정의:
- **채운 필수 역할 수**: 팀원 가운데 기획자와 웹 프로그래머를 서로 다른 학생에게 맡길 때 최대로 채울 수 있는 수(0, 1, 2). 한 학생이 둘 다 할 수 있어도 하나로만 센다.
- **필수 역할 자리 검사**: 학생 X가 팀 T에 들어간다고 할 때 `남는 자리 = 4 - (T의 팀원 수 + 1)`, `못 채운 필수 역할 = 2 - (T의 팀원 + X로 채운 필수 역할 수)`. `남는 자리 < 못 채운 필수 역할`이면 통과하지 못한다.

## 4. 기능 요구

### 4.1 명단 올리기 (관리자, 공고 2.6절)
- 입력: CSV 파일(`admin_roster_file`), 팀 수(`admin_team_count`, 1 이상). `admin_start`를 누르면 실행한다.
- CSV는 `utf-8-sig`로 읽어 BOM이 있어도 된다. 열은 `student_no,name,main_role,sub_roles`이고, `sub_roles`는 `;`로 구분하며 비어 있을 수 있다. 앞뒤 공백은 지운다.
- 역할 이름이 6개 밖이거나 열이 맞지 않으면 아무것도 바꾸지 않고 `막힘: (이유)`를 보여 준다.
- 성공하면 관리자 계정만 남기고 지원, 투표, 팀원, 팀, 학생, 마감 표시를 모두 지운 뒤, 명단의 학생(비밀번호 `1234`의 bcrypt 해시)과 팀 수만큼의 빈 팀(팀1, 팀2, ...)을 만든다. `승인: 명단을 올림(학생 N명, 팀 M개)`

### 4.2 지원 (학생, 공고 2.4절)
지원 단추(`apply_{팀 번호}`)를 누르면 아래 순서로 검사한다. 하나라도 걸리면 접수하지 않고 `막힘: (이유)`를 보여 주며 DB에 기록하지 않는다.

1. 모집이 마감됨
2. 이미 팀이 있음
3. 결과를 기다리는 지원이 있음
4. 팀이 꽉 참(4명)
5. 같은 주 역할의 팀원이 있음
6. 필수 포함 역할을 맡을 학생의 자리가 모자람(3절의 필수 역할 자리 검사. 3장 "필수 포함 역할을 지킬 수 없는 팀"의 어려운 해결)

1~3에 해당하면 지원 단추를 모두 비활성화한다(공고 2.8절). 4~6은 단추를 누른 뒤 `막힘`으로 막는다.

통과하면:
- 빈 팀이면 바로 팀원이 된다. `승인: 팀N에 들어감`
- 팀원이 있으면 대기 지원으로 접수한다. `대기: 팀N 팀원의 투표를 기다림`

### 4.3 투표 (학생, 공고 2.4절)
- 투표할 사람은 **투표하는 때의** 그 팀 팀원 모두다. 지원 뒤에 새로 들어온 팀원도 투표한다.
- 내 팀의 대기 지원마다 지원자 이름, 역할과 함께 찬성(`vote_yes_{지원자 학번}`), 거부(`vote_no_{지원자 학번}`) 단추를 보여 준다.
- 이미 투표한 지원은 단추 대신 `내 투표: 찬성`처럼 보여 준다. 투표는 바꿀 수 없다.
- 거부가 하나라도 나오면 다른 팀원을 기다리지 않고 바로 거절한다. `거절: 팀원이 거부함`
- 지금 팀원이 모두 찬성하면 **승인 직전 재검사**를 한다(3장 "같은 팀에 대기 중인 지원이 여럿"의 어려운 해결): 정원, 주 역할 중복, 필수 역할 자리. 통과하면 승인되어 팀원이 되고, 걸리면 거절한다(`거절: 같은 주 역할의 팀원이 있음` 등). 처리 순서는 지원한 순서가 아니라 투표가 끝난 순서다.
- 아직 투표하지 않은 팀원이 있으면 대기다. 투표한 사람의 `result`에는 그 지원의 지금 상태를 보여 준다(`승인`, `대기`, `거절`로 시작).
- 대기 중인 지원은 승인 직전 재검사 전에는 미리 거절하지 않는다.

### 4.4 모집 마감 (관리자, 공고 2.5절 1~2항)
- `admin_close`를 누르면 마감 표시를 하고, 대기 중인 지원을 모두 거절하며, 팀원이 1명뿐인 팀의 학생을 팀에서 뺀다. `승인: 모집을 마감함`
- 이미 마감했으면 `막힘: 이미 마감함`
- `unassigned`에 팀이 없는 학생의 이름을 보여 준다.

### 4.5 배정 (관리자, 공고 2.5절 3~8항)
`admin_assign`를 누르면:
0. 마감 전이면 `막힘: 모집을 마감하지 않음`. 팀이 없는 학생이 없고 모든 팀이 규칙을 지키면 AI를 부르지 않고 빈 배정안을 만든다(`승인: 배정할 학생이 없음`). 다시 누르면 새 배정안으로 바꾼다.
1. **가능성 검사**: 앱의 스스로 배정(4.6절)으로 규칙을 모두 지키는 배정이 있는지 먼저 확인한다. 없으면 AI를 부르지 않고 `assign_status`에 `규칙을 지키는 배정이 없음`과 이유(예: `팀3에 웹 프로그래머를 맡을 학생이 없음`)를 보여 준다. `result`는 `막힘: 규칙을 지키는 배정이 없음`
2. **AI 배정**: 1차, 2차, 3차 모델 순으로 부른다(5절). 모델마다 요청한 때부터 응답을 다 받을 때까지 **전체 120초**를 재서 넘으면 끊고 다음 모델로 넘어간다.
3. **배정안 검사(5가지)**: 팀이 없는 학생이 빠짐없이 배정됨, 한 학생은 한 팀에만, 모든 팀이 2~4명, 팀 안에 주 역할 중복 없음, 필수 포함 역할 충족. 이미 팀에 있는 학생을 옮기거나 없는 학생, 없는 팀을 쓴 안도 실패로 본다.
4. 응답 없음, 빈 응답, 오류, JSON이 아님, 검사 실패는 모두 실패로 보고 다음 모델로 넘어간다.
5. **3차까지 실패**하면 앱이 스스로 배정한다(4.6절).
6. 기다리는 동안 `assign_status`에 `2차 모델(모델 이름)의 응답을 기다리는 중(최대 120초)`처럼 몇 차 모델을 기다리는지 보여 준다(3장 "AI 대기 중 화면"의 어려운 해결). 끝나면 각 모델의 결과(성공, 실패와 이유)를 함께 보여 준다.
7. 검사를 통과한 배정안만 관리자에게 보여 준다(학생 이름, 역할, 배정된 팀, 누가 만든 안인지). `result`는 `승인: 배정안을 만듦(만든 곳)`
- 최악의 경우 120초 x 3 + 스스로 배정이라도 10분 안에 끝난다(공고 6.3절 18번).

### 4.6 스스로 배정 (3장 "3차 모델까지 실패"의 어려운 해결)
- 팀이 없는 학생(최대 8명)을 팀(3~4개)에 넣는 모든 경우를 백트래킹으로 따져, 5가지 검사를 모두 통과하는 배정을 끝까지 찾는다. 4^8 = 65,536가지 이하라 금방 끝난다.
- 정원, 주 역할 중복이 깨지는 가지는 바로 잘라 낸다.
- 하나도 없으면 "규칙을 지키는 배정이 없음"과 이유를 돌려준다.
- 이유 찾기 순서: (1) 팀이 없는 학생 수가 빈자리보다 많거나, 빈 팀을 2명씩 채울 학생이 모자람, (2) 꽉 찬 팀에 필수 역할이 빠짐, (3) 어떤 팀에 모자란 필수 역할을 맡을 수 있는 남은 학생이 없음, (4) 그 밖에는 `팀마다 따로는 가능하지만 함께 만족하는 조합이 없음`

### 4.7 확정 (관리자)
- `admin_confirm`을 누르면 배정안을 지금 DB 상태로 한 번 더 검사한 뒤 `tf_members`에 저장한다. `승인: 배정안을 확정함`
- 보여 준 배정안이 없으면 `막힘: 확정할 배정안이 없음`

### 4.8 다른 사람의 변경 보기 (3장 어려운 해결)
- 로그인한 뒤의 화면(팀 목록, 지원 단추, 투표, `result`, 관리자의 `unassigned`)을 `st.fragment(run_every=5초)`로 감싸 5초마다 바뀐 부분만 다시 그린다. `refresh` 단추는 두지 않는다.

- 보내는 내용: 지금 팀 구성(팀원의 학번, 이름, 주 역할, 보조 역할), 팀이 없는 학생과 역할, 3절의 규칙. 받는 형식: `{"assignments": [{"student_no": "...", "team_no": 1}]}`
- 호출마다 결과를 `tf_ai_logs`에 남긴다(모델, 성공 또는 실패 이유, 걸린 시간). README 5항의 근거로 쓴다.
- 무료 한도: 하루 50회, 분당 20회. 채점 기간에는 30회 이상 남겨 둔다.

## 6. 화면과 key (공고 2.7절)

화면 글자는 자유이고 key는 표와 똑같이 쓴다. 영문, 숫자, 밑줄만 쓴다.

| 화면 요소 | Streamlit 요소 | key |
|---|---|---|
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input`(type=password) | `login_password` |
| 로그인 단추 | `st.form_submit_button` | `login_submit` |
| 로그인한 사람 표시 | `st.container` | `whoami` |
| 결과 안내 | `st.container` | `result` |
| 팀 하나의 표시 | `st.container` | `team_1`, `team_2`, ... |
| 지원 단추 | `st.button` | `apply_1`, `apply_2`, ... |
| 찬성, 거부 단추 | `st.button` | `vote_yes_{학번}`, `vote_no_{학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 처음 상태 만들기 | `st.button` | `admin_start` |
| 모집 마감 | `st.button` | `admin_close` |
| 팀이 없는 학생 | `st.container` | `unassigned` |
| AI 배정 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 | `st.button` | `admin_confirm` |

- `result`의 안내는 반드시 `승인`, `대기`, `거절`, `막힘` 가운데 하나로 시작한다. 관리자 단추도 같다.
- 학생 화면: `whoami`, `result`, 팀 목록(팀마다 팀원의 이름, 주 역할, 보조 역할, 내 팀이면 `내 팀` 표시, 팀이 없으면 `아직 팀이 없음`), 지원 단추, 내 팀의 대기 지원과 투표 단추
- 관리자 화면: `whoami`, `result`, 명단 올리기, 마감, `unassigned`, AI 배정, `assign_status`, 배정안 표, 확정, 팀 목록
- 설계 결정: 직접 시험할 때 계정을 바꿀 수 있도록 로그아웃 단추(key `logout`)를 둔다.

## 7. 데이터 (`schema.sql`, 공고 5장)

| 테이블 | 열과 제약 |
|---|---|
| `tf_students` | `id` PK, `student_no` UNIQUE, `name`, `main_role` CHECK(6개 역할), `password_hash`, `is_admin` |
| `tf_student_sub_roles` | `student_id` FK, `role` CHECK(6개 역할), PK(`student_id`, `role`) |
| `tf_teams` | `id` PK, `team_no` UNIQUE, `name` UNIQUE |
| `tf_members` | `team_id` FK, `slot_no` CHECK(1~4), `student_id` FK UNIQUE, PK(`team_id`, `slot_no`) |
| `tf_applications` | `id` PK, `team_id`, `student_id`, `status` CHECK(대기, 승인, 거절), `reason`, `created_at`, `decided_at`. 학생당 대기 지원 1개를 보장하는 부분 유일 인덱스 |
| `tf_votes` | `application_id`, `voter_id`, `vote` CHECK(찬성, 거부), PK(`application_id`, `voter_id`) |
| `tf_settings` | `key` PK, `value` |
| `tf_ai_logs` | `id` PK, `created_at`, `model`, `outcome`, `detail`, `seconds` |

- `tf_members`의 PK와 `student_id` UNIQUE가 "마지막 자리에 두 명이 동시에 들어감"(어려운 해결)과 "한 학생은 한 팀"을 DB에서 지킨다. 유일성 위반이 나면 그 처리를 되돌리고 `막힘` 또는 `거절`로 안내한다.
- 지원과 투표 처리는 한 트랜잭션 안에서 해당 팀 행을 잠그고(`SELECT ... FOR UPDATE`) 검사와 기록을 함께 한다.
- 배정안은 관리자 세션(`st.session_state`)에만 두고, 확정할 때 DB에 저장한다.
- 시각은 UTC로 저장하고 화면에는 한국 시각으로 보여 준다.

## 9. 보안과 키 (공고 4.1절, 6.3절)

- `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 `.env`(내 PC)와 Streamlit Secrets(배포)에만 둔다. `.gitignore`에 `.env`가 있다.
- 코드와 화면, 로그에 키나 DB 주소를 출력하지 않는다. 확인은 "있음, 없음"만 한다.
- 비밀번호는 bcrypt로 해시해 저장하고, 로그인할 때 해시와 비교한다. 비밀번호가 틀리면 로그인하지 않는다.
- 문서와 캡처에는 가상 학생만 쓴다.

## 10. 시험과 배포

- `rules.py` 단위 시험: 필수 역할 자리 계산(공고의 예 2개 포함), 주 역할 중복, 5가지 검사, 스스로 배정이 가능한 경우와 불가능한 경우
- 시나리오 시험: 연습 시나리오 3개의 모든 단계를 `service.py`로 실행해 안내 첫 단어가 기대 결과와 같은지, 확정 뒤 규칙을 지키는지 확인한다. AI 없이 스스로 배정으로도 확인한다. 실제 Supabase를 쓰므로 데이터가 초기화된다.
- 직접 시험: 내 PC의 `streamlit run`과 배포한 앱에서 연습 시나리오를 손으로 해 보며 README 5~7항의 근거(화면 캡처)를 모은다.
- 배포: Streamlit Community Cloud, 비공개 저장소의 `main`, 앱 파일 `streamlit_app.py`. 배포 뒤 공개 설정으로 바꾸고 시크릿 창에서 로그인 화면을 확인한다.
- DB 일시정지 막기: GitHub Actions 예약 작업이 매일 `select 1`을 보낸다. `DATABASE_URL`은 GitHub 저장소 Secrets에 둔다.
